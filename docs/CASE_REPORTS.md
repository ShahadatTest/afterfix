# Durable synthetic case reports

Backend accepted after350 Python tests passed on2026-10-28 (23 focused report tests, real release Rust in recovery flows, offline fake Meta). This is consistency validation for the bounded synthetic inventory domain, not a tamper-proof audit or production recovery guarantee. Current frontend integration is a separate pending task.

Each completed investigation attempts ONE durable case capture without rerunning Meta. Response adds `case_id` (string or null) and `case_recording_status` (`recorded` or `unavailable`). Recording failure leaves the actual investigation result available and never silently retries a paid request. New authenticated viewer/operator GET routes:

- `/incidents/{incident_id}/cases`: `{incident_id,cases:[...]}`; at most20 summaries, newest first. A summary includes case_id,incident_id,product_id,proposal_id,recorded_actor_id,created_at,status,stop_category,data_label; invalid rows have record_status invalid/status needs_review. Summary status is the ORIGINAL investigation outcome; fetch full report for current recovery state.
- `/cases/{case_id}/report`: versioned JSON derived from one consistent read-only SQLite copy. GET never calls Meta or changes recovery/audit. Unknown case404; unsupported/missing incident404 on listing; generic errors hide internals. Existing authentication/permissions apply.

Report version1 fields:

- `schema_version:1`, `case_id`, `data_label:"synthetic"`, `incident_id`,`product_id`,`proposal_id` (nullable), `recorded_actor_id`/`actor_id`,`created_at` Unix seconds, `record_status` ok/invalid, `recovery_state` proposed/approved/verified/applied_unverified/needs_review, `verification_status` not_run/passed/failed/unavailable.
- `before`: original server capture, availability/failure reason, capture_id, incident/product, exact bounded events/event_ids, patch/raw_patch, fingerprint/snapshot_hash, evidence_binding/binding labels and caveat. Server capture is broader than actual model read_event_ids: distinguish them. Before remains immutable after repair.
- `investigation`/`model_claims`: actual whitelisted status/reason/stop_category, scope/proposal, hypothesis, observations/inferences with cited IDs, uncertainties, read/selected/evidence IDs, bounded trace/counts/model/usage. Model text is a claim; render as text. Public usage retains actual input/output/total_tokens and cost where known, including zero/null; no fabricated metrics or opaque provider reasoning.
- `initial_proposal`: original investigation proposal with id/proposal_id, incident/product, credit_qty, reverse_event_ids,snapshot_hash,status,reason,created_at. `initial_preview`: actual original preview (below), null or exact unavailable marker `{available:false,status:"unavailable",reason:"initial_preview_unavailable"}`. Never confuse an unavailable marker with a usable preview.
- `current`: incident/product/events/fingerprint/snapshot_hash, current proposal, approvals/audit/repair_events. May be null or explicit unavailable scope/history marker. `current_proposal`, root `approvals`/`audit` are also present for ordinary valid reports. Before/initial preview and current snapshots serve different purposes.
- `final_verification`: null, unavailable marker, or actual `{product_id,final_stock,pass,preservation_verified,checks:[{name,ok,detail?}]}`. Only exact pass true AND preservation_verified true AND nonempty all-passing checks yields verified. Current proposal must be applied and original evidence/preview valid. Proposed/approved stale current fingerprint, missing/unbound data or unavailable preview yields needs_review. Applied repair changes fingerprint legitimately; verification recomputes current preservation from saved approved baseline.

Invalid stored records return record_status invalid/recovery_state needs_review with before/investigation/initial_preview/initial_proposal/current/final_verification null and verification_status not_run. UI must tolerate absent optional collections and unavailable variants. Bounded current scope/history yields explicit unavailable/needs_review, not fabricated complete data. Unknown versions, duplicate/nonfinite/oversized JSON and inconsistent evidence/proposal/preview/Rust bindings fail closed.

Exact initial preview shape: proposal (nested IDs/hash), status,before_stock,after_stock,credit_qty,reverse_event_ids,preserved_restock_ids,unrelated_products,diff:{stock_delta,events_added,restocks_untouched},simulation_checks,simulation_pass,invariants,snapshot_match,rust_verification. It stays the ORIGINAL preview100to110 even after current stock110. Backend `/proposals/{id}/preview` has this same nested proposal contract; no root snapshot_hash alias.

Rust verified shape: enabled true,status verified,verifier_version0.1.0,snapshot_hash,checks,ledger_actual,expected_stock,outstanding_credit,reverse_event_ids,proposal_matches. Failure has status/error_code/hash/optional known version. Approval/apply audit Rust shape is a smaller exact subset: verifier_version,snapshot_hash,ledger_actual,expected_stock,outstanding_credit,reverse_event_ids. Rust approval/apply evidence refers to the PRE-MUTATION snapshot (canonical ledger100, expected110), not a fabricated post-write Rust invocation. Audit apply detail contains approval_id,credit,before,after,reversed,actor_id,rust_verification; approve detail approval_id,snapshot,actor_id,rust_verification. Approval baseline version2 includes original hash/before/after/credit/restock/unrelated/all bounded products/events. Unsupported detail/baseline is explicitly unavailable; no credentials/idempotency keys exported.

Captured scope <=200 target events, patch<=8000 characters, note<=500, description<=2000, combined stored blobs<=512KiB, depth<=8. SQLite owns storage; fixed Rust owns no writes. Existing actor/snapshot/approval/idempotency/transaction gates are unchanged. Reset is an authorized synthetic demo reset and clears saved cases with its other demo data.
